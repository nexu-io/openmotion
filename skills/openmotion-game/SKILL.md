# OpenMotion Game Studio

Turn a one-line brief into a playable local single-player game. Resume an explicitly supplied single-player game id, or use `openmotion_game_create` with a prompt and optional genre, style and setting. Read `openmotion_game_get` before editing. Use the market's Remix action on a single-player template to create an owned draft. If the user requests multiplayer, explain that Game Studio creates single-player games and ask before adapting the brief. Existing multiplayer projects can still be played and inspected.

1. Ask about local-market publication only when that decision is needed. Reuse answers and authorization already supplied. When the plan includes paid media (step 3), include the asset list and spend consent in the same question batch.
2. Read [game design](references/game-design-system.md), [style](references/game-stylization.md) and [genre recipes and quality floor](references/game-genres.md); for a **Format: playable ad** brief also read the [playable-ad recipe](references/game-playable-ad.md), which overrides the title-screen, session and end-card rules. Choose the matching recipe (free-form briefs: pick the closest and say which) and copy its must-haves and acceptance checks into the plan. The quality floor is mandatory: a game-first full-screen playfield (never a landing-page layout with a hero headline beside a small game box), a goal readable in three seconds, at least three kinds of feedback, a 30–120 s session with a ramp, restart in two seconds or less, and characters with real silhouettes instead of bare primitives. Propose the visual direction and one English **60–90 word style formula** covering rendering, shapes, palette roles, light and perspective. Preserve explicitly selected style; resolve unclear direction before costly assets. Save the formula in `design/style.md` and write `design/plan.md` with `openmotion_game_write_files`: experience formula, target metrics with numeric thresholds, reference route must win / idle must lose, and the wave/difficulty plan. Write `design/assets.csv` with at least asset, source, license and cost. Starter drafts are inputs to revise for this brief, not completed acceptance records.
3. **Multimodal-first assets.** For playable ads, follow the recipe and keep all assets inline in the HTML. For other games, Decide per asset whether it is generated, bundled or authored in code (see [Multimodal-first asset routing](#multimodal-first-asset-routing)). When the brief needs a realistic or anime character portrait, a polished illustration, cover, poster or key art, background music or spoken character lines, and discovery shows a fitting model, generate real assets instead of drawing people with Canvas primitives or shipping a silent game. Follow the `openmotion-media` provider order and consent rules: discover with `openmotion_media_use`, state the planned list and provider/model, get spending approval, then submit with `openmotion_assets_use action=generate`, poll `action=status` on the original job and never auto-retry a paid request. Use [textures](references/game-textures.md), [2D](references/game-2d-animation.md), [3D](references/game-3d-animation.md), [procedural motion](references/game-procedural-animation.md) and [audio](references/game-audio.md) as needed. Reference completed assets directly from game code by their library URL `/motion-api/assets/<assetId>/versions/<versionId>/media`; do not try to push binaries through `openmotion_game_write_files` (text only, never base64).
4. Set `building` with `openmotion_game_set_status`. Write `index.html` and optional `client.js`, `style.css`, `logic.js`, `assets/**` (text files) with `openmotion_game_write_files`, id and a batch of `{path,content}`. Preserve the game id and existing decisions. Read [flow and logic contract](references/game-flow.md). New games receive the arcade-2d kit (full-screen canvas, local fixed-step loop over logic.js, keyboard/mouse/touch/one-button input, feedback helpers, best score, portrait switch, test hook and pilot-based referenceRoute). Start from the kit you received; replace its sample rules, art and strings, keep its loop, input layer and hooks, and preserve relative paths and licenses. Code controls, win/loss/restart and loading/error states, not just an attractive scene. Load generated media with a visible loading state and a code-drawn fallback so a missing asset never blanks the game.
5. Before publication run **`openmotion_game_simulate` twice** with one player and the planned tick budget: `scripts:"reference"` must finish with winners, and `scripts:"idle"` must finish with no winners and the intended loss state. A tick-budget timeout is not a loss. Use the game-provided exported `referenceRoute(playerIndex)` or explicit tick routes; keep these ordinary validated actions, never state edits. Record exact inputs, terminal ticks, summary and known limits in **`design/verification.md`**. Run `openmotion_game_validate`; fix diagnostics and address advisory warnings for missing covers or fewer than 20 approximate changed starter-kit lines. A low line count is a signal to inspect the requested gameplay, not an instruction to add filler. Read [the rubric](references/review-rubric.md). **Never operate, attach to or capture the user's visible browser, existing Chrome profile or desktop.** Use **`openmotion_game_playtest`** for server-owned headless testing, with one client and **always pass explicit per-client `scripts`** that exercise this game's real controls (movement keys, skills, clicks on its own buttons). Review console errors, failed requests (generated-media URLs included), screenshots, RAF pacing and each pass/fail assertion. The kit exposes `window.__omGame={getState,getStats,sendAction}` and `?debug` (FPS, draw calls, entities, tick). Playtest reads the player state and verifies the phase, requires scripted net displacement >0.5 world units by default, and checks horizontal overflow at 390×844. Missing hooks fail state assertions. If `scripts` is omitted, each client only holds `D` for 350 ms (move right); that default is a smoke check, not gameplay evidence, and fails movement for games not bound to `D`. Test movement and the win, loss and restart states that apply to the game. Touch controls are required; distinguish implemented touch controls from actual touch-device acceptance. If Chrome/loopback is unavailable, report the exact blocker and unverified checks; never fall back to the user's browser.
6. Set concise title/description/controls and `zh-CN` translations through `openmotion_game_update_meta`. **Use `openmotion_game_capture_cover` for every gameplay cover**, with optional room, input actions and delay. It starts isolated headless Chrome on the server, screenshots only the game canvas/#game root at 1280×720 to `assets/cover.png`, and sets cover metadata. Never use a desktop/full-window screenshot containing tabs, address bars, profiles or other apps. A generated key-art image may appear in-game or on the title screen, but it does not replace the game-only capture requirement. Inspect the capture diagnostics and image rather than assuming a nonempty PNG proves gameplay. Set ready after checks; publish locally only with existing publication authorization. Update design/verification.md with tested revision, inputs, thresholds, actual results and gaps; never leave starter pending rows presented as completed. Validation reports one non-blocking reminder per missing design artifact. Report returned warnings, actual screenshot paths and playtest evidence. Publish returns three nextSteps prompts, using the plan's Follow-up opportunities section when available; show them as optional user prompts and do not execute them automatically. Server headless results do not establish human fun, real GPU/mobile performance or audible quality.
7. **Online sharing is separate from the local market.** `openmotion_game_publish` lists the game only in this workspace's local market. Only when the user explicitly asks for a public link (and the OpenDesign account is signed in), call `openmotion_assets_use` with `action:"web_publish"` and `webPublish:{command:"publish",targetKind:"game",targetId:"<game-id>"}`; use `command:"status"` / `"unpublish"` / `"list"` to inspect or stop sharing. Web publish uploads a static file snapshot (excluding `design/`, `assets/playtests/` and `trailer/`), bundles referenced library media and rewrites complete literal `/motion-api/assets/...` URLs found in supported text files to relative paths; PNG/JPEG library assets at or above 256 KiB are re-encoded to WebP as `_shared-assets/<assetId>-<versionId>.webp` when a local encoder is available (lossless WebP for PNGs to preserve exact RGBA pixels/alpha, quality 82 for JPEGs), and original bytes are kept otherwise. For standard multiplayer games whose `/rooms/` WebSocket runs in the local process, explain before publishing that the public link is a static snapshot, give the local room link for local multiplayer, and never promise remote room hosting unless an actual remote room service is verified. Report the returned link and verify media loading; never claim internet hosting from local publication. When the user wants the game on WeChat, follow [the WeChat Mini Game guide](references/wechat-minigame-port.md): guide them in this conversation one step at a time with `openmotion_game_wechat` (read `status` first; the right-side panel only shows progress), and port the game into `wechat-minigame/` with its smoke test.
8. **Final message to the user** (plain language, the user's language, no tool names, file dumps, ids or JSON): one bold line saying what is playable now (say "playable first version" when limits remain); the play link (and the public link if web publishing was requested); two to four bullets on how to play, the controls and, for an existing multiplayer game, the local room invitation; what was verified and what was not (human fun, real devices, sound); the cost note (no paid generation used, or the approved spend and the provider/model per asset); the cover path. If asked about cost, report only exact spend from tool results, otherwise say it is unknown and name what you will not generate from now on.

## Multimodal-first asset routing

Apply the `openmotion-media` rules (`openmotion://workflow/media/start`) for provider choice, consent and job recovery; this section only maps game asset roles to them.

1. **Discover first.** `openmotion_media_use` `action:"inspect"`, then `action:"models"` with `refresh:true` and the needed `modality` (`image`, `video`, `audio`); add `action:"reference"` with the provider ID before building parameters. Prefer the signed-in OpenDesign account (`account`), then OpenDesign Cloud (`opendesign`), then another configured provider. Use only model IDs the live catalogue returns; the names below are routing hints at review time, not a promise of access.
2. **Route by role.**

| Game asset role | Preferred OpenDesign model when listed | Fallback when nothing fits |
|---|---|---|
| Key art, character portraits, visual-novel scenes, UI art, icons, backgrounds, textures | `gpt-image-2.6-sunburst` / `gpt-image-2.6-flare` (edits, references, transparent background where listed); `seedream-5.5` / `seedream-5.0-flash` (fast, painterly or photoreal) | Code-drawn sprites with outlines and two-tone shading; say generation was unavailable |
| Background music (loops, menu, boss) | `elevenlabs-music-v2` (`mode:"text-to-audio"`; prompt instrumental, `no vocals`) | Web Audio synthesized music loop |
| Character voice, narration, announcer lines | `elevenlabs-v3` (English and multilingual), `byteplus-tts-2` (Chinese voices) | Subtitles only; never fake speech with beeps |
| Cutscene, intro, motion reference clips | `wan-2.7` (short clips), `doubao-seedance-2-5-260628` (longer or 21:9/480p) | In-engine animated scene |
| Short SFX (hit, jump, coin, UI) | No dedicated SFX model at review: synthesize with the Web Audio API in game code | Same |
| 3D models, rigging, animation clips | No 3D generation or rigging model at review: bundled CC0 GLBs plus Three.js procedural modelling | Same; report the boundary |

3. **Approve, submit, poll.** One consent question lists every planned asset (role, count or duration, provider/model). When waiting for that consent on required assets, stop after planning (`design/style.md`, `design/plan.md`, `design/assets.csv`) and the single consent question — do not spend a full turn building and playtesting a throwaway fallback before the user replies. After approval, submit each with a unique `requestId`, poll `action:"status"` with the returned `jobId`, and inspect the result (`action:"read"`) for both usability and rendering-medium fidelity (anime/2D briefs must look like 2D/2.5D anime illustration, never live-action photography) before wiring it in. A queued job is not an asset.
4. **Wire into the game.** Embed each completed version's complete literal `/motion-api/assets/<assetId>/versions/<versionId>/media` URL directly in game source (`<img>`, `Image()`, `fetch` + `decodeAudioData`, `<audio>`, `<video>`, `THREE.TextureLoader`, or a runtime manifest stored outside `design/`); never construct the URL dynamically by string concatenation or `web_publish` will not rewrite it. Playtest, cover capture and trailer serve these URLs from the same local service, and `web_publish` rewrites literal URLs for the public bundle (verify media loading after publish). Record asset id, version id, provider/model, license and approved cost in `design/assets.csv`.
5. **Declined or unavailable.** If the user declines or no fitting model is listed, build the code-made fallback from the table, mark the asset `authored code` in `design/assets.csv`, and say what was not generated. Do not substitute a code-made stand-in while a consent question is still unanswered.

## After publication: optional gameplay trailer

Offer to make a gameplay trailer after publishing. With the user's request, call `openmotion_game_trailer` with `{id,action:"start"}`, then read `{id,action:"status"}`. Do not claim completion until status is `ready`; report `projectId` and `videoUrl`. This creates a separate editable native Motion project in the user's project catalog. Use the existing project-opening operation to open it when requested. The recording is silent; adding generated music afterwards is a separate approved media request. Never use the user's browser or desktop for trailer footage.

The server records three real five-second headless gameplay clips at 1280×720, builds a roughly 19-second title/highlights/Play now composition and uses the existing verified MP4 export pipeline. Chrome, ffmpeg and the pinned native export runtime must already be available; the tool does not download or install them. Automated movement/fire/skills are sampling inputs, not proof of a winning run or human acceptance. Inspect the footage and final video. Failed jobs retain their clips and any created project; report the error and unverified stages.

## Mandatory multiplayer entry acceptance

This section is for diagnosing or verifying playback of existing multiplayer projects.

Every multiplayer game joins on load from `new URL(location.href).searchParams.get('room')`; generate a short random room id when missing. The local play entry redirects missing-room URLs to `?room=...` and preserves other query parameters on both API prefixes. The client must still handle a missing parameter for standalone/embedded use, including opaque sandbox origins where history replacement may fail. Never ask the player to type a room code or perform a Join room step.

- [ ] Opening the game joins within five seconds, with no click or typing.
- [ ] Lobby displays the room code, a Copy invite link button and one primary Start button; one player can start. Copy uses the current room in the invite URL. No room-code input or Join room button, on desktop or touch.
- [ ] `openmotion_game_validate` passes: room-code text inputs or Join room/加入房间 buttons in index.html/client.js are blocking diagnostics. A missing room-query read is an advisory warning; static heuristics do not prove automatic joining.
- [ ] `openmotion_game_playtest` reports the `autoJoin` assertion passed for every client before it clicks Start or executes scripts. Evidence is the room socket's joined message or `window.__omGame.getState()` with selfId and the corresponding player. Joining after five seconds or only after an input fails, even if later gameplay works. Report unavailable Chrome/loopback separately.
