# OpenMotion Game Studio

Turn a one-line brief into a verified local single-player browser game. Resume an explicitly supplied game id, or call `openmotion_game_create` (**always pass `style: "3d"` on any 3D brief** so vendored Three.js is scaffolded) and read `openmotion_game_get` before editing. Use Remix on a read-only template to create an owned draft. If the user requests multiplayer, explain that Game Studio creates single-player games and ask before adapting the brief; existing multiplayer projects can still be played and inspected. Starter drafts (`plan.md`/`verification.md`) are inputs to revise, never completed acceptance evidence.

## Intake, Routing & Priority

Ask **at most two short questions** only when missing: local-market publication consent and (when multimodal assets are planned) the single upfront asset/spend confirmation. Pick the routing tuple before authoring `design/plan.md`:

| Dimension | Selection Rule | Reference |
|---|---|---|
| **3C & Visuals** | Pick 1: `discrete-ui` / `realtime-2d` / `realtime-3d` | [game-3c-modules.md](references/game-3c-modules.md) + [game-feel-craft.md](references/game-feel-craft.md) |
| **Core Loop** | Pick 1 primary (+ ≤ 1 secondary): `puzzle-pressure` / `strategy-combo` / `skill-flow` / `progression-rng` | [game-genres.md](references/game-genres.md) |
| **Track** | **`Full Track`** if ANY of: `realtime-3d`, `puzzle-pressure`, `strategy-combo`, multi-level progression (including playable ads), or generated multimodal assets. **`Fast Track`** otherwise. | [game-gates.md](references/game-gates.md) |
| **Playable Ad** | When brief says **Format: playable ad**: overrides title, session, end-card, no-storage ban, single-file inline `index.html`, and §10/§11 QA | [game-playable-ad.md](references/game-playable-ad.md) |
| **Reference & Blind-Spot Lookup** | Whenever the brief names a reference game ("like X"), targets a non-trivial genre, or hits 3D physics/drift, FPS aim/recoil, solvable dealing, or WFC/A* triggers | [game-lookup.md](references/game-lookup.md) |

**Priority order:** `1. Hard safety / IP-piracy / runtime / spend boundaries` > `2. Explicit user intent ([locked] reference game, visual style, spatial layout, rules)` > `3. Verified 3C / readability / gate contracts` > `4. Open creative exploration` (when visual style is left open, explicitly reject the genre's default cliché and starter-kit graybox shell rather than repeating a house look; never override an explicit user style or layout). Track routing here and in `game-gates.md` governs the run; **Fast Track** supersedes the 5-stage sequence in `game-design-system.md`.

**Runtime & tool discipline:** Keep `logic.js` deterministic and fast (`< 5 ms` per tick; keep tunables in one top `config` block; emit bounded transient `events[]` instead of storing cosmetic particles or O(N²) loops in `logic.js`). Batch cohesive multi-file edits into single `openmotion_game_write_files` calls, always pass the exact game `id`, and never operate or capture the user's visible browser or desktop.

## Workflow

1. **Brief, Creative Hook & Lookup.** Read [brief standard](references/game-brief.md), [style](references/game-stylization.md), and your routed 3C/Loop references. Write `design/plan.md` (routing tuple, open-style cliché self-negation when style is unlocked, **1 Signature Twist + 1 Peak Moment**, 3–5 game-specific Hard Fails, reference-win/idle-loss contract, and wave/difficulty plan), `design/style.md` (60–90 word English formula), and `design/assets.csv` (planning high-impact generated images, short video clips, and audio whenever fitting models are listed). Run [game-lookup.md](references/game-lookup.md) when triggered.
2. **Multimodal-first assets.** Do **not** assume zero-asset code-only visuals by default. For playable ads, follow the recipe and keep all assets inline in the HTML — never trigger media sign-in or upgrade prompts on playable ads. Pure code-driven gameplay-first games without an explicit request for generated art, voice, music, or video stay outside media setup, sign-in, and upgrade prompts (matching Motion's pure-native boundary: do not call, suggest, or ask about generation in that case). For games that plan generated multimodal assets, route generation through `openmotion-media` (`openmotion://workflow/media/start`) and [Multimodal-first asset routing](#multimodal-first-asset-routing): when live discovery lists fitting usable OpenDesign/provider capabilities or models (`mediaEntitlement` is `included` or signed-in `unknown`, not `not-included`), obtain one upfront spend consent (skip if already granted or enforced by the host's tool-approval gate), submit via `openmotion_capability_run` (preferred when exposed, especially for executable atomic capabilities reported with `status:"live"` and `available:true` such as `remove-background`, `relight`, `image-blend`, `camera-control`, `music`, and `speech`) or `openmotion_assets_use action=generate`, poll `openmotion_job_manage` / `action=status`, inspect via batch contact-sheet `openmotion_asset_manage` / `openmotion_assets_use` `action=read`, and embed each completed asset by its literal library URL `/motion-api/assets/<assetId>/versions/<versionId>/media` (never base64 via `openmotion_game_write_files`). Use [textures](references/game-textures.md), [2D](references/game-2d-animation.md), [3D](references/game-3d-animation.md), [procedural motion](references/game-procedural-animation.md), and [audio](references/game-audio.md) as needed. When no fitting model is usable for explicitly requested art/character/voice/music assets, follow the setup-routing rule below to surface the setup/upgrade choice upfront.
3. **Build (`set_status("building")`, `write_files`).** Execute your Track in [game-gates.md](references/game-gates.md) following [game-flow.md](references/game-flow.md). Replace the neutral graybox starter's placeholder palette, rules, and strings completely while keeping its fixed-step loop, input layer, `window.__omGame` hook, `?debug` overlay, and `pilot`/`referenceRoute` pattern. Load generated media with visible loading states and code-drawn fallbacks so a failed asset never blanks gameplay.
4. **Verify (fast logic first, focused browser checks).** Run `openmotion_game_validate`, 3-tier `openmotion_game_simulate` (`reference` terminal win via a concrete player-facing milestone even on endless designs; explicit degraded weak route struggling/losing; `idle` terminal loss inside `< 2500` ticks), and consolidated `openmotion_game_playtest` runs with explicit per-client `scripts` exercising real controls (3C Hard Fails, peak-density `390×844` layout, active Level-2/mid-game state, console/network cleanliness, generated-media URL loads). Use fast local logic sweeps for balance math when shell access exists instead of looping repeated browser renders. Review against [review-rubric.md](references/review-rubric.md) and log measured results + `Known gaps (P2)` in `design/verification.md`.
5. **Deliver (`capture_cover` → `verification.md` → `validate` → `update_meta` → `ready` → authorized `publish`).** **Use `openmotion_game_capture_cover` for every gameplay cover** (isolated server Chrome, 1280×720 canvas PNG to `assets/cover.png`); inspect diagnostics and image before setting `zh-CN` metadata via `openmotion_game_update_meta`. Remember `write_files` demotes `ready` to `building` — finish closure cleanly before replying. Show returned `nextSteps` as optional user prompts without executing them automatically. Server headless results do not establish human fun, real GPU/mobile performance, or audible quality.
6. **Online sharing is separate from local publication.** `openmotion_game_publish` updates only the workspace catalog. When the user requests a shareable web URL, call `openmotion_assets_use` (`action:"web_publish"`, `targetKind:"game"`, `command:"publish"|"status"|"unpublish"|"list"`), following the static snapshot, literal URL rewrite, WebP compression, and multiplayer-caveat rules in [game-flow.md](references/game-flow.md). If `web_publish` fails because OpenDesign is signed out (`OPENDESIGN_SIGN_IN_REQUIRED` / `AUTH_REQUIRED`), do not retry in a loop — explain that online publishing requires signing in with OpenDesign and direct the user to click the inline "Sign in & publish" action card (or Publish button), then reply to retry. Inside Studio / Super Agent, do **not** also call `openmotion_open_preview(target:"providers")` or present `/settings/providers` as a web artifact (the inline publish sign-in card already handles sign-in in place); only external MCP-only hosts without Studio's inline card should call `openmotion_open_preview` with `target:"providers", entry:"agent_media_signed_out"`. Never imply public hosting from local publication.
7. **Final message to the user** (plain language, the user's language, no tool names, file dumps, ids or JSON): one bold line saying what is playable now (say "playable first version" when limits remain); the play link (and public link if requested; for existing multiplayer projects include the direct `?room=<id>` invite URL); concise controls + 3–5 top `config` tuning levers verified against final code; verified vs unverified (human fun, real devices, sound); cost note and cover path; then up to five numbered P2 polish items per [game-gates.md](references/game-gates.md#reporting-p2-to-the-user).

## Multimodal-first asset routing

Apply the `openmotion-media` rules (`openmotion://workflow/media/start`) for provider choice, consent and job recovery; this section only maps game asset roles to them.

1. **Discover first.** When Unified Capability Center meta-tools are exposed, start with `openmotion_capability_discover` (`action:"list"`, `action:"providers"`, `action:"models"` with `refresh:true` and the needed `modality`), and pass `modality` (`"image"`, `"video"`, or `"audio"`) to `openmotion_media_use(action:"inspect", modality=...)` when checking setup for a specific asset type so an image-only provider does not hide a missing audio/video handoff; otherwise use `openmotion_media_use` (`action:"inspect"`, `action:"models"` with `refresh:true`, and `action:"reference"` with the provider ID before building parameters). Prefer the signed-in OpenDesign account (`account`), then OpenDesign Cloud (`opendesign`), then another configured provider. Select models dynamically from the live discovery metadata (`tier`, `bestFor`, `description`, `mode`, `supportsImageReference`, `maxInputImages`, `generationOptions`) and never guess unlisted model IDs or parameters.
2. **Route by role and capability traits.**

| Game asset role | Capability / live-discovery routing rule (OpenDesign first) | Fallback when nothing fits |
|---|---|---|
| Key art, hero portraits, visual-novel scenes, title/cover art | `text-to-image` / `image-edit`: pick an OpenDesign `image` model with `tier:"flagship"` (matching `bestFor` / `description`, e.g. `hero-art`, `character-portraits`, `painterly-scenes`, `text-rendering`); require `supportsImageReference:true` for reference edits | Code-drawn sprites with outlines and two-tone shading; say generation was unavailable |
| Batch sprites, props, tiles, cards, UI icons | Pick an OpenDesign `image` model with `tier:"fast"` (matching `bestFor` such as `batch-sprites`, `transparent-cutout`, `batch-tiles`, `card-art`); prefer models whose `generationOptions` list `background:"transparent"` for cutouts | Same |
| Sprite cutout / relighting / multi-ref blend (atomic edits) | Dedicated capabilities via `openmotion_capability_run` when discovery reports both `status:"live"` and `available:true`: `remove-background`, `relight`, `image-blend` (never simulate background removal or relighting with ad-hoc prompts when executable) | Native `background:"transparent"` on generation or key-color chroma-key in game code |
| Background music (loops, menu, boss) | `music` capability or OpenDesign `audio` model with `mode:"text-to-audio"` (`bestFor` matching `bgm-loop`); prompt instrumental, `no vocals` | Web Audio synthesized music loop |
| Character voice, narration, announcer lines | `speech` capability or OpenDesign `audio` model with `mode:"text-to-speech"`, selecting by `bestFor` / `description` (e.g. `zh-speech` for Chinese, `multilingual-speech` for English/multilingual) and live `generationOptions` voices | Subtitles only; never fake speech with beeps |
| Cutscene, intro, motion reference clips | `image-to-video` / `camera-control` / `multi-shot` or OpenDesign `video` model with `maxInputImages >= 1`, choosing short/fast vs longer duration from `tier`, `bestFor`, `description`, and live `nativeOptions`/`generationOptions` | In-engine animated scene |
| Short SFX (hit, jump, coin, UI) | Check live `audio` discovery for a dedicated SFX model (`bestFor` matching `sfx`); when none is listed, synthesize with the Web Audio API in game code | Web Audio API synthesis |
| 3D models, rigging, animation clips | **Reserved 3D gateway slot**: check live discovery (`modality:"3d"` / `3d-asset` capability) first; use newly exposed 3D mesh/rig models automatically once `status:"live"` and `available:true`, otherwise use bundled CC0 GLBs plus Three.js procedural modelling | Same; log slot in `design/assets.csv` and report the boundary |

3. **Approve, submit, poll.** One consent question lists every planned asset (role, count or duration, provider/model) — skip re-asking if consent was already granted in the prompt or the host already enforces a tool-approval gate for generation. When waiting for that consent on required assets, stop after planning (`design/style.md`, `design/plan.md`, `design/assets.csv`) and the single consent question — do not spend a full turn building and playtesting a throwaway fallback before the user replies. After approval, submit independent assets concurrently with unique `requestId`s via `openmotion_capability_run` (or `openmotion_assets_use action:"generate"`), poll `openmotion_job_manage` / `action:"status"` with the returned `jobId`, and inspect completed images together in one batch contact-sheet `read` (`openmotion_asset_manage` or `openmotion_assets_use`, `items:[{assetId,versionId},...]`) for usability, alpha, and rendering-medium fidelity (anime/2D briefs must look like 2D/2.5D anime illustration, never live-action photography) before wiring them in. A queued job is not an asset.
4. **Wire into the game.** Embed each completed version's complete literal `/motion-api/assets/<assetId>/versions/<versionId>/media` URL directly in game source (`<img>`, `Image()`, `fetch` + `decodeAudioData`, `<audio>`, `<video>`, `THREE.TextureLoader`, or a runtime manifest stored outside `design/`); never construct the URL dynamically by string concatenation or `web_publish` will not rewrite it. Playtest, cover capture and trailer serve these URLs from the same local service, and `web_publish` rewrites literal URLs for the public bundle (verify media loading after publish). Record asset id, version id, provider/model, license and approved cost in `design/assets.csv`.
5. **Unavailable, plan-gated, or low-balance recovery.**
   - **Already usable Plus+ or BYOK provider:** never prompt for sign-in or upgrades.
   - **Ordinary gameplay-first game without explicit multimodal asset requests (and Playable Ads):** stay completely outside media setup, sign-in, and upgrade prompts (matching Motion's pure-native boundary) — build and deliver the playable code-made game directly, mark assets `authored code` in `design/assets.csv`, and do not call `openmotion_open_preview` or suggest media upgrades unless the user asks for generated assets.
   - **Art / character / voice-led game with no usable model** (user explicitly asks for character art, portraits, anime visuals, visual-novel cast, voice acting, or custom BGM): call `openmotion_open_preview` using the modality-scoped `settingsHandoff` from `openmotion_media_use(action:"inspect", modality=...)` — carrying `entry:"agent_media_signed_out"`, `"agent_media_upgrade_free"`, `"agent_media_upgrade_go"`, or `"agent_media_key_rejected"` — and pause in one turn with two clear options: (1) sign in / upgrade to OpenDesign Plus (or save an API key) and reply to continue with AI assets, or (2) build a playable code-placeholder prototype first. After the user confirms setup, re-inspect (`openmotion_media_use` `action:"inspect"`, then `action:"models"` with `refresh:true`) and resume.
   - **Plus+ low balance:** do not pre-block on cached `hasBalance`; if a real generation request fails with low balance (`balance is too low` / `insufficient_balance`), stop without retrying, call `openmotion_open_preview` with `target:"providers", entry:"agent_media_balance_low"`, and ask the user to top up and reply to resume.
   - **User declined:** build the code-made fallback from the table, mark the asset `authored code` in `design/assets.csv`, and say what was not generated. Do not substitute a code-made stand-in while a consent question is still unanswered.

## After publication: optional gameplay trailer

Offer to make a gameplay trailer after publishing. With the user's request, call `openmotion_game_trailer` with `{id,action:"start"}`, then read `{id,action:"status"}`. Do not claim completion until status is `ready`; report `projectId` and `videoUrl`. This creates a separate editable native Motion project in the user's project catalog. Use the existing project-opening operation to open it when requested. The recording is silent; adding generated music afterwards is a separate approved media request. Never use the user's browser or desktop for trailer footage.

The server records three real five-second headless gameplay clips at 1280×720, builds a roughly 19-second title/highlights/Play now composition and uses the existing verified MP4 export pipeline. Chrome, ffmpeg and the pinned native export runtime must already be available; the tool does not download or install them. Automated movement/fire/skills are sampling inputs, not proof of a winning run or human acceptance. Inspect the footage and final video. Failed jobs retain their clips and any created project; report the error and unverified stages.

## Mandatory multiplayer entry acceptance

This section is for diagnosing or verifying playback of existing multiplayer projects.

Every multiplayer game joins on load from `new URL(location.href).searchParams.get('room')`; generate a short random room id when missing. The local play entry redirects missing-room URLs to `?room=...` and preserves other query parameters on both API prefixes. The client must still handle a missing parameter for standalone/embedded use, including opaque sandbox origins where history replacement may fail. Never ask the player to type a room code or perform a Join room step.

- [ ] Opening the game joins within five seconds, with no click or typing.
- [ ] Lobby displays the room code, a Copy invite link button and one primary Start button; one player can start. Copy uses the current room in the invite URL. No room-code input or Join room button, on desktop or touch.
- [ ] `openmotion_game_validate` passes: room-code text inputs or Join room/加入房间 buttons in index.html/client.js are blocking diagnostics. A missing room-query read is an advisory warning; static heuristics do not prove automatic joining.
- [ ] `openmotion_game_playtest` reports the `autoJoin` assertion passed for every client before it clicks Start or executes scripts. Evidence is the room socket's joined message or `window.__omGame.getState()` with selfId and the corresponding player. Joining after five seconds or only after an input fails, even if later gameplay works. Report unavailable Chrome/loopback separately.
